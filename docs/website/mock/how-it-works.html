How it works

業務面と AI 面を、
Bridge v1 でつなぐ。

業務システムは唯一の正本のまま。AI 面（DSH）は会話と記憶だけを持ち、業務データは必要なときに本人の委託で読みます。2 つの面は、版の付いた HTTP プロトコル Bridge v1 と、機械が読める自己紹介 manifest でつながります。

業務面が持つもの

業務データ、職員と役割、規則、承認、金額、監査、通知の受信者と本人の通知設定、AI 社員のプロフィール（版と監査）、マニュアルの索引。会話は持ちません。

AI 面が持つもの

会話、AI 社員の設定（人物・使えるツール）、チャットの接続、自動タスクの台帳、長期記憶。業務データは持たず、必要なときに本人の委託でツールから最新の値を読みます。

Five layers

5 つの層

依存の向きは L5 → L3 / L2 → L1。L3 は L2 を知らず HTTP だけで話すので、業務システムは Node.js でなくてもつながります。

層部品役割
L1 protocol@dsh-bridge/protocolBridge v1 の OpenAPI 3.1、manifest と event の JSON Schema、検証ライブラリ、bridge-validate CLI、適合性テスト（52 項目）
L2 server-kit@dsh-bridge/server-kit業務システム側の Node.js 部品。連携コード・委託・outbox・通知・承認・報告・提案・manifest 配信・個人情報の検査など。業務が書くのは hooks だけ
L3 AI 面@dsh-bridge/dsh-core + 9 pluginsアプリの登録、業務 API クライアント、委託のキャッシュ、ツールの部品、AI 秘書の文面の枠、送信の検査
L4 Webgateway · web-kit業務 Web の BFF から AI 面への認証付きゲートウェイと、React の画面部品
L5 adapterあなたのシステムmanifest、hooks（または既存 API の別名）、手書きのツール・文面のモジュール、承認・提案の画面
Main flows

主な流れ

① 業務の変化 → 通知（規則ベース・モデルを使わない）

01業務の行と event を同じトランザクションで（outbox）
02取り込み：少なくとも 1 回・再試行・dead letter
03業務システムが受信者を解決
04まとめ送信・おやすみ時間・配信先の優先順位
05本人の 1:1 に AI 秘書の文面

② 質問と委託（AI 社員は本人の権限で読む）

01職員がチャットで質問
02発信元で身元を照会（未連携なら何も返さない）
03委託を取得：AI 許可リスト ∩ 役割、最長 5 分
04本人の範囲だけを読む
05本人の 1:1 に答える

③ 提案と承認（決めるのは人、1 回だけ）

01AI が読取で確かめる
02提案：POST /proposals → pending_review
03人が採用・却下（1 回）／承認カードをワンタップ
04採用時だけ業務システムが書込む

④ 自動タスクと定時報告

01event や時刻で AI 社員を起こす（playbook）
02委託の分類で決めた職員の権限で読む
03必要なら提案
04受信者に 1 通（固定の文面）・送信前の検査
Principals

誰として呼び、何ができるか

主体誰できること
サービスAI 面（DSH）身元の照会・委託の発行・event・通知の解決・承認カード・manifest。業務データは読めない
委託職員の代わりの AI 社員（最長 5 分）本人の役割で許された読取と提案だけ。書込み・承認・確定は 403
職員のセッション業務 Web を使う本人連携コードの発行・自分の連携・通知設定・提案の採否・承認
BFF業務 Web のサーバアシスタントのチケット・添付の変換・本人のボットの登録

1 つの AI 面に複数のシステム

会話・記憶・自動タスク・通知はアプリごとに分離。トークンとツールもアプリをまたがない。

🧱

stateless な Bridge v1

セッション・回数制限・コード・委託・event はすべて PostgreSQL。業務側は台数を増やせる。

隔離して動かす AI 面
