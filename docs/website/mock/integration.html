Integration

旧いシステムにも、
新しいシステムにも。

業務ロジックの書き換えは不要。ただし、何も変えずにつながるわけではありません。業務システムに「ブリッジ」を足し、残りはフレームワークが用意します。

足すのは「ブリッジ」

  • 業務データを読む口と、AI の提案を受ける口
  • manifest（システムの自己紹介）
  • 本人の SNS 連携（システム自身のログインで）
  • 受信者を業務システムが決める規則
  • 状態変化を同じトランザクションで event に
  • 承認の規則・定時報告（件数だけ）

載せ方は 3 通り

  • Node.js：既存のサーバに server-kit を載せ、hooks を既存の表と関数につなぐ
  • 同じ働きの API がある：/bridge/v1 を既存のルートに別名で載せる
  • Node.js 以外：OpenAPI 3.1 をその言語で実装し、適合性テストで確かめる

生まれたときから、AI 社員と働く

  • server-kit の上で作れば、Bridge の部分は部品が持つ
  • 書くのは業務・hooks・manifest・画面だけ
  • 見本の業務システムで、構成と書き方を確かめられる
project layout
bridge.manifest.yaml   # self-description
src/auth.mjs           # authenticate · isSessionLive
src/domain.mjs         # business rules · tx + emitEvent
src/hooks.mjs          # employees · recipientsFor · approvals
src/routes.mjs         # /api/* · readToolPolicy
manual/NN-*.md         # one screen = one section
test/conformance.test.mjs
web/  bff/             # web-kit · gateway

コードを変えずに、外にブリッジを置く

  • ログインを外から確かめられる（OIDC / SAML）
  • 本人として呼べる API がある
  • commit 後の変化の知らせ（webhook / CDC）がある
  • 承認と書込みの API がある
A4 つともある → 全機能
BAPI はあるが本人として呼べない → 知らせと報告まで
C画面しか無い → API を足すか、新規で
Checklist

業務システムに足すもの（13 項目）

承認と定時報告は、業務で使わなくても最小の形で持ちます（適合性テストを skip なしで通すため）。

#足すもの区分
1業務データを読む口と、AI の提案を受ける口必須
2manifest（--strict で警告なし）必須
3本人の SNS 連携の画面（システム自身のログインで）必須
4受信者を業務システムが決める規則（Web の認可と同じ判定）必須
5状態変化を同じトランザクションで event に必須
6職員と役割（有効・無効を含む）必須
7承認の規則を 1 か所の関数に必須
8Web のセッションの確認必須
9職員向けのマニュアル（1 画面 = 1 節）推奨
10名簿に基づく個人情報の検査推奨
11AI 社員のプロフィールの編集推奨
12定時報告（件数だけ）必須
13外部連携（接続先・操作・規則）任意
Seven steps

7 ステップと、完了の条件

1manifest を書いて検証
2hooks を実装（または別名）
3トランザクションで event
4適合性テスト 52 / 52
5AI 面の profile に登録
6業務 Web に画面と BFF
7自動タスクを有効化
done when

node profile/scripts/check.mjs cordis.patch.yml   exit 0
# 8 business web
tsc --noEmit                            no errors
