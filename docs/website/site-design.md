## 1. コンセプト

### 1.1 ひとことで

**「どの IT システムも、考えて動く AI 社員の職場へ。」**

登録・照会・更新を待つだけだった業務システム（レガシー IT）に「ブリッジ」を足すと、AI 社員が生まれ、職員一人ひとりのチャットで
知らせ・頼み・下書きし・覚える。サイト全体で **旧い IT → ブリッジ → 知能の時代** という時間の流れを見せる。

### 1.2 伝えたいこと（優先順）

1. **変化**：画面を開いて待つシステムから、自分から動くシステムへ（Before / After）。
2. **3 つの力**：考える・覚える・自分から動く。決めるのはいつも人。
3. **どのシステムにも**：既存システムにブリッジを足す（業務ロジックの書き換えは不要。ただし何も変えずにつながるわけではない）。新規開発も同じ部品で。
4. **安全は設計で**：本人の権限まで・受信者は業務システムが決める・個人情報を載せない・閉じた既定・52 項目の適合性テスト。
5. **開発者が信頼できる**：Bridge v1（OpenAPI）・manifest・server-kit・conformance・skill。

### 1.3 読み手と導線

| 読み手 | 知りたいこと | 主な導線 |
|---|---|---|
| 経営層・事業責任者 | 何が変わるか、人手不足と確認・催促の時間にどう効くか | ヒーロー → Before/After → 3 つの力 → 一日の様子 → 相談 |
| 情報システム部門・技術管理層 | 既存システムにどうつながるか、安全か | 仕組み → 安全 → つなぎ方 → 技術解説（PDF / ページ） |
| 開発者・SIer | 何を実装すれば良いか | 開発者 → manifest / hooks / conformance → GitHub・skill |

### 1.4 トーンとことば

- 未来的・技術的だが、**誇張しない**。数字は事実だけ（52 項目・9 プラグイン・12 種のチャットなど）。効果の数字は「試算例」と明記する。
- 「必ず」「すべて自動」「何も変えずに」「業界初」は使わない。価格・競合の名前は載せない。
- AI 社員は AI であることを常に示す（「— さくら（受注管理 AI 秘書）」）。
- 画面例の名前・数値・業務はすべて架空。実在の顧客名・環境名は載せない。

## 4. トップページの文案

### 4.1 ヒーロー

- バッジ：`BUSINESS SYSTEM × AI EMPLOYEE · Bridge v1`
- 見出し（3 行、2・3 行目をグラデーション）：
  - どの IT システムも、
  - **考えて動く**
  - **AI 社員の職場へ。**
- 本文：
  Bizアシスタントは、登録・照会・更新を「待つ」だけだった業務システムに、小さな「ブリッジ」を足します。
  すると AI 社員が生まれ、職員一人ひとりのチャットで知らせ、頼み、下書きし、覚えます。業務ロジックの書き換えは不要。決めるのは、いつも人です。
- CTA：［導入を相談する］（主）／［技術解説を読む］（副）
- 補足：既存システムにも新規開発にも ・ Slack / LINE / Teams ほか ・ 52 項目の適合性テストで検証
- ビジュアル（アニメーション）：
  - 左「LEGACY SYSTEM」：灰色の表（受注番号・状態・期限）、カーソルが点滅、「人が開くまで待っている」
  - 中央「BRIDGE v1」：光の粒が左から右へ流れる（event → AI）。下に `manifest` `events` `delegation` のチップ
  - 右「AI 社員」：スマホ型のチャット。【対応のお願い】出荷期限を過ぎた受注が 3 件…が順に表示され、［確認する］ボタン

### 4.2 数字の帯

| 値 | ラベル |
|---|---|
| 52 | 適合性テストの項目（Bridge v1） |
| 9 | AI 面のプラグイン |
| 12 | 個人ボットで使えるチャット |
| 0 | AI が確定・承認・支払う操作 |

### 4.3 時代の移り変わり

- 見出し：**IT は「記録する道具」から、「一緒に働く同僚」へ。**
- 3 つの時代：
  - 記録の時代：台帳と入力。人がデータを入れる。
  - 画面の時代：CRUD と業務ロジック。人が画面を開き、確かめ、追いかける。
  - **知能の時代**：AI 社員が見張り、知らせ、頼み、下書きし、覚える。人はチャットで決める。
- Before / After（左右の対比）：
  - Before：人が画面を開くまで待つ ／ 大事な変化に気づくのが遅い ／ 承認のために人を追いかける ／ 報告書を作る
  - After：AI 社員が先に気づく ／ 関係する人にだけ届く ／ チャットのワンタップで決まる ／ 定時のまとめが届く

### 4.4 3 つの力

| 力 | 説明 | 例（チャット） |
|---|---|---|
| 考える | 本人の権限の範囲で業務データを読み、いま大事なことを見分け、計画書や修正の案を下書きする | 「AI の提案が 2 件あります。採用か見送りかをお決めください。」 |
| 覚える | 一人ひとりの好みと用件、組織の手順、前の会話を覚える（個人情報は覚えない） | 「承知しました。報告は結論から 3 行にします。」 |
| 自分から動く | 変化を見張り、関係する人にだけ知らせ、適任者に頼み、進まなければ催促する | 「【至急】09:00 開始予定の出荷作業が、まだ始まっていません。」 |

締めの一文：**AI は読む・提案する。確定・承認・金額の決定は、いつも人。**

### 4.5 AI 社員のいる一日

08:30【定時のご報告】対応が必要なこと 2 件 ／ 09:20【至急】未開始の作業 ／ 14:00【承認のお願い】ワンタップで承認 ／ 16:00【対応のお願い】AI の提案 2 件。
注記：画面はすべて架空の例です。

### 4.6 仕組み

- 見出し：**業務システムはそのまま正本。AI 社員は、ブリッジの向こうで働く。**
- 図：業務システム（データ・規則・承認・監査）⇄ **Bridge v1 + manifest** ⇄ AI 面（会話・記憶・自動タスク・9 プラグイン）⇄ いつものチャット
- 4 ステップ：① 業務の変化を同じトランザクションで記録 ② 業務システムが受信者を決める ③ AI 社員が本人の権限で読み、提案する ④ 人がチャットで決め、結果は業務システムに記録
- 5 層のチップ：L1 protocol ／ L2 server-kit ／ L3 AI 面 ／ L4 web-kit・gateway ／ L5 あなたのシステム

### 4.7 安全は設計で

| カード | 一文 |
|---|---|
| 決めるのは人 | AI の書込みは「提案」だけ。採用・承認は人が 1 回 |
| 本人の権限まで | AI の権限 ＝ AI に許した操作 ∩ その職員の役割（最長 5 分のトークン） |
| 届け先は業務システムが決める | AI は宛先を選ばない。関係する人にだけ届く |
| 個人情報を載せない | event は ID・日付・件数だけ。送信前の検査と固定の文面 |
| 閉じた既定 | グループ会話・無人の処理・送信先は既定で閉じている |
| 52 項目で検証 | 約束は適合性テストで確かめる |

### 4.8 つなぎ方（タブ）

- 既存システム：足すのは「ブリッジ」——読む口と提案の口、manifest、本人の SNS 連携、受信者の規則、トランザクションの event、承認と報告。同じ働きの API があれば別名で載せられる。Node.js 以外は OpenAPI を実装。
- 新規開発：server-kit の上で作れば、Bridge の部分は部品が持つ。書くのは業務・hooks・manifest・画面だけ。
- 外付けモード（試行）：既存システムに SSO・本人として呼べる API・変化の知らせがあれば、コードを変えずに外にブリッジを置ける。
- 7 ステップ：manifest → hooks → event → 適合性 52 → profile → 業務 Web → 自動タスク

### 4.9 開発者

- 見出し：**仕様は OpenAPI。約束はテストで。**
- コード：manifest（YAML の抜粋）と `createBridgeApp({ hooks })`（JS の抜粋）
- ターミナル：`node --test conformance/http.test.mjs` → `52 passed, 0 known gaps, 0 skipped`
- リンク：技術解説（PDF）／ガイドライン／導入 skill（AI コーディングエージェント用）／GitHub（要アクセス権）

### 4.10 対応チャット・運用AI Bot・FAQ・CTA

- 対応チャット：Slack・LINE・Microsoft Teams・WeCom・WeChat・Lark・Telegram・Discord・WhatsApp・QQ・DingTalk・Matrix（email は通知だけ）
- 運用AI Bot：**システムも、自分で育つ。** 課題の受付 → 調査 → 修正・テスト → PR → 承認 → 反映 → 記憶。本番はいつも人の承認。
- FAQ（例）：
  1. 既存システムのコードは変えずに済みますか？ → 業務ロジックの書き換えは不要ですが、ブリッジ（窓口・manifest・規則など）の追加は必要です。最初の診断で一覧にします。
  2. AI が勝手に承認や支払いをしませんか？ → できない作りです。AI の書込みは提案だけで、承認・確定は人が業務システムで行います。
  3. どのチャットで使えますか？ → 上の一覧。組織のボットと、職員が自分でつなぐ個人ボットがあります。
  4. 個人情報はどう扱いますか？ → event と通知に載せず、送信前に検査します。記憶にも残しません。
  5. どの AI モデルを使いますか？ → 導入先が選びます（AI 面の設定）。
  6. Node.js 以外のシステムでも使えますか？ → Bridge v1（OpenAPI）を実装し、適合性テストで確かめればつながります。
- 最後の CTA：**あなたの IT を、次の時代へ。** ［導入を相談する］［技術解説を読む］

### 5.2 文字

- 欧文：Inter（数字・英字・コード以外）、コード：JetBrains Mono。和文：Noto Sans JP（フォールバック Yu Gothic UI / Hiragino / Meiryo）。
- 見出し：800、ヒーロー 56〜64px（スマホ 34〜38px）、セクション見出し 36〜40px（スマホ 26px）。本文 16〜17px、行間 1.8。

### 5.3 モチーフと動き

- **背景の格子と星**：うすいグリッド＋ゆっくり流れる光の粒（canvas）。スクロールでヒーローから遠ざかる。
- **ブリッジの光**：レガシー → AI 社員へ、光の粒が流れ続ける（event の流れの比喩）。
- **時代のタイムライン**：スクロールで左から右へ光が満ちる。
- **カード**：半透明（glass）＋細い発光の縁、ホバーで縁が回転するグラデーション。
- **チャットの吹き出し**：入ってくるたびにふわっと現れる（タイピングのドット）。
- `prefers-reduced-motion` ではすべての動きを止める。

### 5.4 レスポンシブ

- 1200px 以上：12 カラム、ヒーローは文字の下に横長のビジュアル。
- 768〜1199px：カードは 2 列。
- 767px 以下：1 列、ナビはハンバーガー、ヒーローのビジュアルは縦積み（レガシー → ブリッジ → チャット）。左右の余白 16px、横スクロールを出さない。

### 5.5 アクセシビリティ

- 本文のコントラスト比 4.5:1 以上（`--muted` は大きな文字か補足だけ）。
- 動きは装飾だけ。情報は文字でも読める。アニメーションの図には `aria-label` で説明。
- キーボードで全操作（タブ・FAQ のアコーディオン・メニュー）。

## 6. 実装の方針（本番サイト）

- 静的サイト（Astro か Next.js の静的出力）。ページの原稿は Markdown（`/docs` は技術解説の md をそのまま）。

- 計測：プライバシーに配慮した解析（Cookie なし）。お問い合わせフォームは個人情報の扱いを明記。
- 画像：図は SVG（ブランドの色トークンで描く）。製品の実画面は使う場合も架空のデータに差し替える。
- 公開前のチェック：誇張表現・価格・競合名・実在の顧客名・内部の環境名が無いこと、AI 社員の画面に「AI 秘書」の署名があること。
